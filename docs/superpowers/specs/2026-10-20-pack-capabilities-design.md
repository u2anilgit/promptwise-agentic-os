# Pack capabilities and actor-scoped policy — Design

Status: **proposed, awaiting user review.** Written in an autonomous session (2026-10-20). Not implemented. Closes the design gap recorded in `docs/BACKLOG.md` ("`check_policy` capability registration not built … needs a real design pass") and is a Phase 8 prerequisite ("pack signing + pack-scoped capabilities").

## Problem

A pack's `pack.yaml` declares `capabilities` (e.g. `shell:run:ruff`) and a `permissions_rationale`, but nothing turns them into permissions. `check_policy(action)` is a flat first-match over global rules: it has no idea *who* is acting. If installing a pack simply appended `allow shell:run:ruff`, every actor (every agent, every other pack) would gain that right. That silently widens the attack surface on every install, which goal 4 forbids.

## Goals

1. Installing a pack grants its declared capabilities **to that pack only**.
2. The operator sees and approves each pack's capabilities at install time; nothing is granted implicitly.
3. Operator deny rules always win over pack grants.
4. Existing global rules and callers keep working unchanged (backwards compatible).
5. Every grant, use and denial is attributable in the audit log (actor = `pack:<name>`).

## Non-goals

- Pack signing / provenance (separate design; this one assumes the operator trusts what they install).
- Per-user identity (single-operator model stays).
- Runtime sandboxing of pack code (packs ship content and declarative DAGs; core verbs do the acting).

## Design

### D1. Actor on every policy check
`check_policy(action, config, actor: str | None = None)`. `None` keeps today's behaviour (global rules only). Core verbs that act on a pack's behalf pass `actor="pack:<name>"`; agents over MCP pass `actor="mcp"` (the boundary already knows this).

### D2. Rules gain an optional `actors` field
`PolicyRule(action, effect, actors: list[str] | None = None)`. `None` = applies to everyone (today's rules). A rule with `actors` only matches when the caller's actor matches one of them (fnmatch, so `pack:*` works). Evaluation order is unchanged except that **all deny rules are evaluated before allow rules** for actor-scoped checks, so a global `deny shell:run:*` cannot be bypassed by a pack grant. (Global-only checks keep first-match to stay backwards compatible; documented.)

### D3. Install writes a pack-scoped, operator-approved policy file
`promptwise pack install <name>` prints the capabilities and the rationale and requires `--approve-capabilities` (or an interactive yes). On approval it writes `policies/packs/<name>.yaml`:
```yaml
# generated by `promptwise pack install` — remove the pack to revoke
rules:
  - action: "shell:run:ruff"
    effect: allow
    actors: ["pack:stack-python"]
```
and audits `pack_capabilities_granted` with the list and the manifest hash. `pack remove` deletes the file and audits `pack_capabilities_revoked`. Capabilities are validated against a grammar (`fs:read|write:<glob>`, `shell:run:<program>`, `net:fetch:<host>`), and wildcards broader than one program/host are refused unless `--allow-broad`.

### D4. Doctor
`packs.integrity` gains: every installed pack has its policy file, the file's rules match the manifest's declared capabilities exactly (no hand-widened grants), and no pack file grants to an actor other than itself.

### D5. Where `policies/packs/` lives
Under the operator's `paths.policies_dir`, so the hardened-deployment advice (keep policies outside agent-writable roots, `governance.exposure` doctor check) covers it automatically.

## Decisions for the user

1. **Deny-before-allow only for actor-scoped checks** (keeps global behaviour bit-for-bit)? *Recommended: yes.* The alternative (deny-before-allow everywhere) is cleaner but changes the meaning of existing operator files.
2. **Explicit `--approve-capabilities` flag** rather than an interactive prompt (CI-friendly, and the flag shows up in shell history)? *Recommended: flag, with the capability list printed first.*
3. **Refuse broad wildcards by default** (`shell:run:*`, `fs:write:**`)? *Recommended: yes, with `--allow-broad`.*

## Test plan (when implemented)

- A pack grant lets `pack:a` run `shell:run:ruff`; `pack:b`, `mcp` and unscoped callers are still denied.
- An operator `deny shell:run:ruff` beats the pack grant.
- Install without approval writes nothing and grants nothing; remove revokes; both audited.
- Doctor FAILs on a hand-edited pack policy file that widens a grant.
- Existing policy tests pass unchanged (actor `None`).
