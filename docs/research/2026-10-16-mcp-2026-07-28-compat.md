# MCP 2026-07-28 revision — compatibility check

**Date:** 2026-10-16. **Evidence:** the official changelog (`modelcontextprotocol.io/specification/2026-07-28/changelog`, fetched 2026-10-16) and introspection of the installed SDK; migration claims about the Python SDK 2.x come from secondary posts and a throwaway spike (`mcp==2.3.0` in a scratch venv), not from the official migration guide (not read).

## Where we are

- Installed/locked SDK: `mcp 1.29.0`. `SUPPORTED_PROTOCOL_VERSIONS = 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25`. **It does not speak 2026-07-28.** `pyproject.toml` bounds `mcp>=1.27,<2`, so an accidental upgrade to 2.x cannot happen; the lock holds 1.29.0.
- `gateway/mcp_server.py` imports `mcp.server.fastmcp.FastMCP` (removed in SDK 2.x) and reads the private `mcp_app._tool_manager` for pinning.

## What the revision changes, and what it means for us

| Change (official changelog) | Impact on PromptWise | Action |
|---|---|---|
| No `initialize` handshake; version + capabilities in each request's `_meta`; new `server/discover` | A 1.x server speaks the old handshake only. Clients that require the new protocol cannot use us until we move to the 2.x SDK. Older clients keep working during the deprecation window. | Migrate to SDK 2.x as its own change (below). |
| `Mcp-Session-Id` and protocol sessions removed; use explicit, server-minted handles passed as tool arguments | **Already aligned.** Every tool is stateless per call; cross-call state is an explicit argument (`spec_id`, `session_id`). | None. |
| Roots, Sampling, Logging deprecated | We use none of them. | None. |
| Tasks moved to an extension (`io.modelcontextprotocol/tasks`), polling via `tasks/get` | `complete_task`/`verify_output` can take many seconds (Semgrep, test runs); today they block. | Consider the Tasks extension after migration. |
| Multi Round-Trip Requests replace server-initiated requests | We never make server-initiated requests. | None. |
| `resultType` required on results; `CacheableResult` (`ttlMs`, `cacheScope`) on list results; deterministic `tools/list` order SHOULD | `tools/list` order is registration order (deterministic). The SDK should supply the rest. | Re-run `test_mcp_registry_consistency` after migration. |
| HTTP: `Mcp-Method`/`Mcp-Name` headers; SSE resumability removed | We serve stdio today; the HTTP gateway has no MCP endpoint yet. | Apply when an HTTP MCP endpoint is added. |
| Authorization: `iss` validation (RFC 9207), Client ID Metadata Documents preferred over Dynamic Client Registration | We have **no authentication** (backlog). | Implement to the new rules when auth is built, not the 2025-06-18 text that `ADOPTION_AND_CAPABILITY_RESEARCH.md` cites. |
| OpenTelemetry trace context in `_meta` (`traceparent`, ...) | Fits the planned OTel adapter. | Adopt with the OTel work. |
| Error-code renumbering, `-32602` for resource-not-found | SDK concern. | None. |

## Migration spike (SDK 2.3.0, scratch venv)

- `from mcp.server.mcpserver import MCPServer` replaces `FastMCP`; `@server.tool()` decorator unchanged; `list_tools()` still async; `_tool_manager` still exists as a private attribute.
- `list_tools()` items expose `input_schema` (snake_case) instead of `inputSchema` — one test (`test_live_tool_spec_matches_what_clients_are_served`) and any client-shaped assertions change.
- Not yet checked: `call_tool` result shape (our tests parse `blocks[0].text`), stdio entrypoint (`mcp_app.run()`), the `mcp` -> `mcp-types` split, and Python-version floor (3.10+, fine).

## Decision

1. **Stay on `mcp 1.29.x` now**: it is what the 486-test suite and the lock were validated on, and nothing here forces an upgrade before the 12-month deprecation window.
2. **Migrate to the 2.x SDK as a dedicated change** with this acceptance: all gateway tests pass on `mcp>=2,<3` in a lock-built venv; `server/discover` returns the 12 tools; the registry-consistency test still passes (pins are computed from the served text, so they will need re-pinning once if field names change); `.mcp.json` stdio launch verified with a real client; replace the private `_tool_manager` reads with a public accessor if 2.x provides one.
3. Keep tool-description pinning: it is protocol-version independent and matters more in a stateless world where each request can be routed to a different server instance.

The claim in one secondary source that stdio was removed is contradicted by the official changelog and is not relied on.
